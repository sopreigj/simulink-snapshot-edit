# 解释：为什么块型表不需要分版本

这篇讲一个**被实测推翻的预期**：我们原以为跨版本要给 `snp_block_source`分版本（或加版本列），实测后证明不需要。想知道表是什么去看[参考：块型覆盖](../reference/block-coverage.md)。

## 预期 vs 实测

**预期**：R2025a / R2026a 库会大量重命名、新增、弃用块型，R2023b 的表（核心库 119 条，后经跨版本验证扩至 200 条）在新版本会大面积失效，需要版本分表或版本列。

**实测**（大规模验证为该项目早期的私有工程资产，已移出本仓库；数字为该资产下的实测结论，见 CHANGELOG 历史段）：
- R2023b 导出的 25 份快照在 **R2026a 上重建并复导出逐字节一致**（CROSS 25/25）；
- 三版本各自跑全套（导出 / 重建 / 特殊块 / 行为 / roundtrip）**全绿**，表的所有条目在新版本**无一失效**；
- R2025a 穷举 61 库 / 121 种 BlockType，表覆盖 114，**真缺口仅 1 个**（`SimscapeArrayConnection`）；
- R2026a 穷举 64 库 / 134 种，表覆盖 121，**真缺口同样 1 个**（同上）。

## 为什么漂移这么小

三个结构性原因（不是运气）：

1. **块型是稳定层**。Simulink 的 BlockType 语义跨版本高度稳定——库名、库内路径会变，但"Gain 就是 Gain"不变。表存的是 BlockType→库路径，前者稳定，后者才是风险点——而后者受原因 2 保护。
2. **有 rb 的块不走表**。导出时**优先走 ReferenceBlock**，表条目仅是无 rb 时的回退。大部分工具箱块在模型里有 rb，库名变化根本到不了表。
3. **Simscape 块共用 BlockType**。`fl_lib` 块数从 311（2023b）涨到366（2026a），但这些物理块共用 `SimscapeBlock` 一个 BlockType——块数增长不产生新的表条目需求。

## 唯一的表条目失效，不是路径漂移

`PMComponent`（`sps_lib/Passives/Mutual Inductance`）在 R2026a 失效。全库搜索确认：**powersys（Specialized Power Systems）产品整个下线**，2026a 全库零命中——不是"路径变了"，是"东西没了"。

处置：表条目不动。理由：
- 若 2026a 模型真有 PMComponent 块，它的 rb 会指向已下线的库——解析失败是**版本外部事实**，不是本工具的责任范围；
- 历史验证资产不用 PMComponent（三版本重建 25/25 IDENTICAL 已证）；
- 真要 powersys→Simscape Electrical 的等价功能是**语义迁移**（参数不同），不是表条目替换——那需要单独立项。

## 什么时候需要动表

- **新版本出现新 BlockType**：跑一遍发现机制（见[参考：块型覆盖](../reference/block-coverage.md) 最后一节），把新增条目追加到同一张表。旧版本模型不含该块型，多出的条目永远不触发，**零副作用**。
- **块型真的换了库路径**（目前实测零例）：加条目时优先确认有 rb 的块不受影响。

一句话：**表是"实测快照"，不是"运行时动态查库"**——枚举机制通用（换库名可重跑），入表结果写死（该版本下已验证的事实）。这套口径（机制通用 + 结果写死 + rb 优先 + 单表）让跨版本维护成本趋近于零。
